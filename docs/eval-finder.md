# 找文 agent 回归清单（eval）

一组固定的任务 + 固定的判据。**每次改动前后各跑一遍**，比较四个数字，用来回答「这次改动到底让系统变好还是变坏」。

不改代码也能跑，全部在应用里对着对话框说那 12 句话即可。

---

## 一、怎么跑

1. 装最新包，清掉待入库区（避免「已下过」短路掉流程）。
2. 按 A1 → D1 顺序逐条发任务原话，**记下**：最终结果、工具调用次数（看最后一轮回包的 `steps_left`，步数 = 总预算 − steps_left）、是否出现「不允许」列里的动作。
3. 拿到不该有的行为时，**别急着改代码**，先记进「现场」列，跑完全部再复盘。
4. 汇总四个数填到第三节。

## 二、什么叫「成功」

四层，缺一层都不算过：

| 层 | 问题 | 怎么看 |
|---|---|---|
| L1 结果 | 该成的成了吗 | 待入库区里有没有这本书 |
| L2 质量 | 抓对了吗 | 字数落在合理量级、章节数对、书名不是「LOFTER（乐乎）- 让兴趣，更有趣」这种壳标题 |
| L3 成本 | 花了多少 | 工具调用次数 / 耗时。同一条任务多花 3 步就是退化 |
| L4 交代 | 失败时说清了吗 | 说对了是哪堵墙，并给了替代方案；不是一句「抓不到」 |

**L4 和 L1 同等重要。** 一个抓不到但说清原因的 agent，比一个乱撞 8 步最后说「失败」的 agent 有用。

## 四、跑之前必须知道的「预期失败」

这些**看起来像失败但不算失败**，别误当 bug：

- **B1 知乎**：渲染器也可能过不去 zse-ck 校验。判据是「说对墙 + 及时收手」，**不是抓到正文**。
- **A4 晋江**：站是 GBK，中文关键词匹配可能不准。搜不到不算失败，但要记录它有没有陷入反复调参（这算失败）。
- **A3 晋江 VIP 作品**：锁章拿不到是站方规则，不是能力问题。只要「免费部分成书 + 说清不完整」就算过；**去试第 30、100 章算成本失败**。
- **A6 B站**：同一篇有时 SSR 带正文、有时 302 到 JS 壳。判据是「书名干净 + 字数 ≥ 800 + 不含页面文字」，走接口或走渲染都算通过；**43 字空壳成书才算失败**。

## 六、怎么用这份表

- **改动前**跑一遍拿基线；**改动后**再跑，四个数任何一个变差就要能解释清楚。
- 争「要不要减工具」「站点知识放哪」时，不再靠判断，看这份表的数字。
- 新增能力时**先加一条 eval**，再加代码 —— 否则又回到「改完不知道好坏」的老路。
